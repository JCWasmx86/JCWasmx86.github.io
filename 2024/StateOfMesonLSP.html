State of mesonlsp

Introduction

Since April 9th, 2024, mesonlsp has been the default language server for the vscode-meson extension. It replaces Swift-MesonLSP and features improved diagnostics, performance, and memory usage. Six days later, I started to collect the downloads of mesonlsp every hour using a script. (For some reason, there are just 23 files for every day.)

Current State

mesonlsp

I mainly fixed a lot of bugs and played catch-up with the Meson API. The biggest new feature is mesonlint, which packages the language server into a nice linter. It's currently Linux-only.

Ecosystem

I'm happy to report that the ecosystem is consistently growing:

  • Zed support by @hqnna

  • Helix support by @RaphGL

  • Packaging in Conda Forge by @danielnachun

  • Packaging in NixOS by @paveloom

  • Packaging in Arch Linux by @polyzen

  • Support for Mason by @Conarius and @FineFindus

  • Emacs support by @judemille

  • Packaging for Alpine Linux by @folliekazetani

Thanks to all these people (and those that I forgot to name), a lot of other people can use mesonlsp. It's incredible how many editors have the supporting code/configuration for mesonlsp. It's amazing how many package repositories it's packaged in. Sure, in the grand scheme of things, it's still not that much, but I'm happy mesonlsp is at this point.

Telemetry

There won't be any automatic telemetry in mesonlsp. If you want to help me by giving me an overview of who uses mesonlsp, please consider adding a comment here. It's a simple and uncontroversial form of telemetry.

Future

Sadly, the time I can invest into mesonlsp is getting less and less. I'm soon working full-time and won't be studying anymore.

mesonlint

For mesonlint to be used, it has to be integrated more tightly with other programs like GitHub Actions or GitLab CI. If anybody is interested in implementing it, feel free to contact me or add a comment to the issue.

mesonlsp

The complaint I heard the most is about the auto-completion. It's a complicated topic - at least for me - but I hope I can improve it in the future. Another unimplemented feature is auto-completion and linting of wrap files.

But with the great achievements @annacrombie made with muon, I think people have to decide whether it would make more sense to move to a muon-based language server. It would probably require a big rearchitecturing, but I think at some point it's nearly inevitable. You have built-in formatting, the linting is probably more advanced, it's faster. I think such a language server would have a lot of merits. I won't do this due to time constraints, but it could be an interesting project to play with.
